## 2. CONFIRMED BUG — Application never leaves "draft" status

### Severity: High (blocks the core adoption lifecycle)

### What happens

1. An adopter calls `POST /api/applications/` to submit an adoption
   application.
2. `Application.status` defaults to `"draft"` (see
   `backend/apps/applications/models.py`, `Status.DRAFT`).
3. `ApplicationViewSet.perform_create` (in
   `backend/apps/applications/views.py`) saves the application without
   ever changing its status away from `"draft"`.
4. The valid-transitions map only allows `draft -> submitted` or
   `draft -> cancelled`.
5. Only staff/admin are permitted to call the `update-status` action
   (`IsAdopter`/adopter role is blocked there — see the permission check
   at the top of `update_status`). Adopters only have access to the
   `cancel` action.
6. Result: there is **no way for an adopter to move their own
   application out of `"draft"`**. Every submitted application is stuck
   until a staff member manually opens it and flips it to `"submitted"`
   themselves, which is backwards — staff should be reviewing submitted
   applications, not performing the adopter's submission step for them.

### Reproduction (verified live against a running server)

```bash
# after registering + verifying + logging in as an adopter, and staff
# creating an available pet:
curl -X POST http://127.0.0.1:8000/api/applications/ \
  -H "Authorization: Token <adopter_token>" \
  -H "Content-Type: application/json" \
  -d '{"pet": "<pet_id>", "why_adopt": "...", ...}'

# GET /api/applications/ as staff afterward shows:
# "status": "draft"
```

### Required fix

Choose ONE of the following approaches and implement it consistently
with the rest of the codebase's patterns (status transitions, audit
logging, notifications):

**Option A (simpler, recommended unless a save-as-draft UX is wanted):**
Set the status to `"submitted"` automatically in
`ApplicationViewSet.perform_create`, immediately after `serializer.save()`,
instead of leaving the model default (`"draft"`) in place. Keep `"draft"`
as a valid status for future save-as-draft support, but do not let normal
submission end there.

**Option B (if save-as-draft is an intentional feature):**
Add an adopter-permitted `submit` action (mirroring the existing `cancel`
action) that transitions `draft -> submitted`, and update
`adopter-portal/src/pages/NewApplicationPage.tsx` to call it after
creation (or expose a separate "Save Draft" vs. "Submit Application"
button pair in the UI).

Either way:

* Add a regression test that calls the actual `POST /api/applications/`
  endpoint (not just the model/serializer) and asserts the resulting
  status is `"submitted"` (or that a follow-up `submit` call succeeds),
  so this class of bug is caught in CI going forward.
* Confirm the existing `AuditLog` and notification behavior still fires
  correctly for this new transition.

## 3. CONFIRMED DEFECT — Create-application response omits `id`/`status`

### Severity: Low (currently harmless, but bad API practice)

### What happens

`ApplicationViewSet.get_serializer_class` returns
`ApplicationCreateSerializer` for the `create` action, and DRF's default
`CreateModelMixin.create()` uses that same serializer to build the
response body. `ApplicationCreateSerializer.Meta.fields` does not
include `id`, `status`, `created_at`, etc., so `POST /api/applications/`
returns only the fields the client submitted — the caller has no way to
learn the new application's ID from the response.

This currently does not break the adopter-portal, because
`NewApplicationPage.tsx` navigates to `/applications` (the list) after a
successful submit rather than to the new record's detail page. It would
break any other client that needs the created ID (e.g. a future
"upload documents immediately after applying" flow, or the staff portal
if it were ever used to create applications).

### Required fix

Override the `create` method (or `get_serializer_class` return per
action more precisely) so the response after a successful create uses
`ApplicationSerializer` (the read serializer) instead of
`ApplicationCreateSerializer`. Keep `ApplicationCreateSerializer` for
validating input on write.

## 4. Items verified as CORRECT — do not "fix" these

To avoid duplicate work or accidental regressions, note that the
following were explicitly checked and found correct:

* Rate limiting / brute-force protection (AGENTS.md §35, §40) — this is
  implemented as account lockout (`MAX_FAILED_LOGINS = 5`,
  `LOCKOUT_MINUTES = 30`) and OTP attempt limiting
  (`MAX_OTP_ATTEMPTS = 5` → HTTP 429), in
  `backend/apps/accounts/views.py`. This satisfies the requirement even
  though it is not implemented via DRF `THROTTLE_CLASSES`.
* Duplicate-application prevention (`AGENTS.md` business rule #3) — both
  a serializer-level check and a DB `UniqueConstraint` exist.
* The 6 required report types (`AGENTS.md` §38) all exist with CSV
  export and staff-only permissions.
* Payment-optional / ₱0-package business rules (`AGENTS.md` business
  rules #4–5) are implemented and explicitly commented in
  `backend/apps/payments/models.py`.
* Audit logging is wired into real state-changing views (adoptions,
  applications, pets, payments), not just defined as an unused model.
